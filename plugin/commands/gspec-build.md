Run the autonomous "idea → built" gspec build: hold the one-time intake interview here, then hand off to the headless `gspec build` runtime, which drives every stage (profile → competitive research (opt-in, `--research`) → stack → practices → style → features → architecture → plans → **spec review** → implement → reconcile) unattended — pausing once at the spec-review gate, after every spec is written and before any code is generated, so the user can review the specs (skippable with `--no-review`) — self-healing each writer/validator and build/test gate.

You are the **front door** to the build. The build itself is a deterministic runtime (`lib/build.js`) that spawns its own isolated headless agent runs per stage, on the engine the user selects (`--engine claude|codex|pi`; when omitted it defaults to the target this project was installed for, recorded in `.gspec/config.json`, else `claude`); the filesystem (the `gspec/` docs) is the shared state, and a run manifest (`.gspec/build/run.json`) makes it resumable. Your job is the **one interactive step it can't do headlessly** — the intake — and then to launch and monitor it.

> **When to use this vs. the individual commands.** This is the full autonomous build for a fresh idea. If the user wants to work one spec at a time with a conversation at each step, point them at `/gspec-profile`, `/gspec-stack`, `/gspec-implement`, etc. — those keep the human in the loop; this does not, after intake.

> **Engine prerequisite.** The chosen engine's CLI must be installed and authed, and gspec must be installed for that engine (`gspec install`, so its agents exist under `.claude/agents/`, `.codex/agents/`, or `.pi/agents/`). Claude uses native `--agent`; Codex and Pi run each stage by injecting the installed agent's instructions. On Pi, if a stage stalls waiting on tool approval, pass `--pi-permission-level` (sets `PI_PERMISSION_LEVEL`).

## Flow

1. **Confirm the idea and preflight.** Take the idea from the arguments below (if absent, ask for it in one line). Then:
   - Check the CLI is available: `gspec --version` (it lives in this repo's `bin/gspec.js`; if the user runs from elsewhere, `node <repo>/bin/gspec.js` also works). If it isn't installed, tell the user and stop.
   - Check gspec is installed **in this project** for an engine: `.gspec/config.json` records the target, or one of `.claude/agents/`, `.codex/agents/`, `.pi/agents/` exists here. If none do, offer to install it for the harness you are running in right now — you know which one you are — with `npx gspec -t <claude|codex|pi>`, then continue. Do not launch the build in a project with no engine installed; it will fail its preflight.
   - Check for an existing run: if `.gspec/build/run.json` exists, **do not start over** — run `gspec build --status` to see how it ended (and where), report that, and offer to **resume** it (step 4 with `--resume`) or to remove the file and restart. Stop for the user's choice.

2. **Intake interview** (the build's one interactive step — done here so it isn't lost to headless mode). Hold a single up-front interview, following the `gspec-authoring` clarification protocol: ask **one question per message**, wait for the answer, then ask the next — never send the whole list at once. Offer 2–3 concrete suggestions per question. These decisions must end up **settled** — the list is not a script, and the interview is as long as the idea needs:
   - **Product type & primary audience** (web app / API / CLI / mobile / library …).
   - **Technology lean** (any framework/language/hosting preferences or hard constraints; otherwise note "architect's choice").
   - **Visual style direction** (a look/feel, an existing brand, or **"no UI"**).
   - **Scope boundaries** — what's in for this build and what's explicitly out.
   - **Known competitors** (names or URLs) — only when the user passed `--research`; the research stage starts from this list, so capture it in the brief.

   **Let the idea set the length.** Where the idea already answers an item, confirm it in one line and move on — an idea that says "a CLI tool" has settled visual direction, and asking anyway wastes the user's turn. Where an item is genuinely open, or a lot rides on it (a system with several moving parts, an ambiguous audience, a constraint that reshapes the stack), stay on it for as many turns as it takes. A five-item list is not a five-question interview: ask nothing you can infer, and stop when the load-bearing decisions are settled rather than when the list runs out. Do not proceed while one is unresolved.

3. **Write the brief.** Assemble a concise brief — the idea plus every decision you just resolved and any clearly-labeled assumptions — and write it to `.gspec/build/brief.md`. This is the exact file the runtime looks for; because it now exists, the build **skips its own intake** and runs fully unattended. Show the user the brief and get a final go-ahead before launching. When asking for the go-ahead, mention that the build will **pause once before implementation** so they can review the finished specs — and that `--no-review` makes it fully unattended if they'd rather not be interrupted.

4. **Launch the build.** The run is long (nine agent-driven stages plus the spec-review pause), so it must outlive a single tool call. **How you launch it decides whether its failure ever reaches the user** — pick the first option that applies:
   - **Preferred — a background task your harness tracks.** If your shell tool can run a command in the background *and notify you when it exits* (in Claude Code: a Bash call with `run_in_background`), use that. This is the only launch method where the user learns about a failure without having to ask: the harness wakes you when the process ends, and step 5 turns that into a report. Take it whenever it is available.
   - **Fallback — detached, and you own the follow-up.** If nothing tracks the process for you, launch it detached and treat the log as the progress feed:
     `nohup gspec build "<idea>" > .gspec/build/build.log 2>&1 &` (note the printed PID).
     A detached run notifies no one. So do not fire and forget: tell the user plainly that you cannot watch it, that they should ping you to check on it, and that `gspec build --status` answers "how did it go?" at any time from their own terminal.
   - Fresh run: `gspec build "<idea>" [--engine claude|codex|pi]` — `--engine` is optional; it defaults to the target this project was installed for (`.gspec/config.json`), else the one engine whose agents are installed here. If neither signal exists, pass `--engine` for the harness you are running in.
   - Resume: `gspec build --resume` (the run stays on the engine it started on, recorded in the manifest — a conflicting `--engine` is ignored). On Pi, re-pass `--pi-permission-level` if it was needed — it is per-invocation, not stored in the manifest.
   - Honor flags from the arguments: pass through `--engine`, `--no-qa` to skip the validator gates, `--qa-retries <n>` to give every QA gate n self-heal revisions before it pauses the run (default 1; also honored on a `--resume`, so a run that paused at a QA gate can be given a bigger budget for the retry), `--no-review` to skip the spec-review pause before implementation, `--research` to run competitive research right after the profile stage (the build fans out web research per competitor and feeds the auto-accepted findings into the feature PRDs; pinned at run start, so it cannot be added on a `--resume`), `--pi-permission-level <level>` for Pi, and offer `--dry-run` first if the user just wants to preview the stage plan (it prints every engine command it *would* run and spawns nothing).
   Because `.gspec/build/brief.md` exists, the runtime skips its own intake and runs fully unattended — never re-interview, and never try to perform the stages yourself; the runtime spawns its own agent for each stage on the chosen engine (`claude` / `codex` / `pi`), under the user's session/auth.

5. **Monitor and report.** Follow progress from the background task's output (or `tail .gspec/build/build.log` when detached, e.g. after each user check-in) and the manifest (`.gspec/build/run.json`) — which stage is running, gate verdicts, and skips.

   **When the run ends, you MUST tell the user how it ended — every time, including when it failed.** A build that dies unreported is the single worst outcome of this command: the user believes work is happening when it stopped hours ago. So the moment the process exits (your background task completes, or the user checks back in), run **`gspec build --status`** and report what it says. Do not infer the outcome from the log's last line, and never let a run end in silence.

   `gspec build --status` prints the run's terminal state and **exits with a code that names it** — read the code, not the prose:

   | Exit | State | What it means |
   | --- | --- | --- |
   | `0` | complete | Every stage finished. Specs + code are in place. |
   | `1` | failed | A stage failed its gate. The run is paused and needs you. |
   | `2` | paused_review | The spec-review human gate. Expected, not an error. |
   | `3` | crashed | The process died without finishing — killed, out of memory, or an internal error. |

   The same state is in `.gspec/build/status.json` if you'd rather read it directly. **Exit 0 means complete and nothing else** — a pause is 2, so you can no longer mistake one for the other. Then handle the ending:
   - **Paused for spec review** (exit 2; log says "Paused for spec review"; manifest `review` stage is `paused`). This is the expected second human gate: every spec is written, no code exists yet. Summarize the specs for the user (`gspec/profile.md`, `research.md` if `--research` ran, `stack.md`, `practices.md`, `style.*`, `architecture.md` + any `architecture/` sub-files, `features/`, `tasks/`), help them review and edit anything they want changed — on a `--research` run, remind them the research findings were **auto-accepted** by the build, so this pause is where to prune any they disagree with, and on their go-ahead relaunch with `gspec build --resume` (background/detached, as in step 4) — that resume **is** the approval and continues into implementation. Do not treat this pause as an error.
   - **Paused on a failure** (exit 1). Surface the failing stage and **why**: the runtime prints the failing verdict/output and keeps it in full in `.gspec/build/last-failure.md` and in the failed stage's `detail` field in the manifest — relay those findings verbatim (not just the one-line reason), and tell the user they can fix the issue and re-run this command to **resume** from exactly there. A gate fails only on a `blocker`/`major` finding, so a pause is a real defect, not polish. The user may **hand-edit the flagged spec** to unblock: on resume, a stage left `failed` re-validates the current on-disk deliverable (their edit is honored, not overwritten), so a hand-fix that resolves the finding lets the run continue. If the failure was a QA gate that just needs more attempts, resume with `--qa-retries <n>`. For tuning the build loop, every QA failure this run — including ones a self-heal already recovered from — is also kept in full in the cumulative `.gspec/build/qa-failures.md` (never auto-removed).
   - **Crashed** (exit 3). The run died without finishing — killed, out of memory, or an internal error. It is not a gate failure and there are no findings to relay: say plainly that the build stopped partway, name the stage it stopped in (from `--status` or `.gspec/build/last-failure.md`), and offer to continue it with `gspec build --resume`, which picks up from exactly that stage. If it crashed twice in the same place, that is worth investigating rather than resuming again.
   - **Build complete** (exit 0; log says "Build complete"). Report that specs + code are in place and point at the run record. Either way, the runtime finishes by printing a **"Learnings recorded this run"** report — the lessons agents captured to memory during the build (promotable via `/gspec-distill`) and the QA feedback events that drove a self-heal; relay it, and surface any captured lessons to the user. The full verdict behind each feedback event (even recovered ones) is in `.gspec/build/qa-failures.md`.
